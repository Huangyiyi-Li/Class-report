# Windows 客户端事故记录

## WIN-REC-009：录音与上传过程不可观测，OSS 凭证字段不兼容

- 状态：已定位并修复，等待 `v0.2.0-codex.12` Windows 真机复测
- 影响版本：`v0.2.0-codex.11`
- 用户现象：绑定后首页长期只显示“录音中”和聚合待上传数量；看不到本次时长、已形成分段和各段处理阶段。“立即重试”没有持续反馈，设置页也无法判断失败发生在设备认证、上传凭证、OSS 文件上传还是录音信息登记。
- 直接根因：服务端现役 OSS 接口返回 `bucket`、`endPoint`、`expiration`，客户端只读取 `bucketName`、`endpoint`、`expireDate` 和并不存在的 `uploadDir`。设备认证成功后仍会在解析上传凭证时失败，分段留在本地队列等待重试。
- 可观测性根因：worker 快照只有聚合的 `pending/completed`，上传失败原因只保存在 SQLite 单条记录中；手动重试命令虽已异步化，但 Electron 的命令确认立即返回，界面因此没有持续显示后台重试过程。
- 修复：兼容服务端现役 OSS 字段；服务端未返回目录时使用稳定对象路径 `ai-lesson-eval/{deviceNo}/{YYYYMMDD}/{fileName}`。首页显示本次录音时长和已完成本地分段；worker 快照区分设备认证、上传凭证、OSS 上传和信息登记，并提供安全的最近 20 条队列诊断；手动重试增加进行中、结果、失败原因和下次自动重试反馈。
- 安全边界：诊断信息不包含 accessToken、STS 密钥、Cookie 或录音完整本地路径；不修改任何服务端代码和接口。

## WIN-REC-008：已删除录音仍计入待上传，补传阻塞录音操作

- 状态：已定位并修复，等待 `v0.2.0-codex.11` Windows 真机复测
- 用户现象：删除录音目录中的旧文件后，客户端重启仍显示 2019 段待上传；点击“立即重试”无反馈，随后“开始录音”也无响应。
- 根因一：待上传状态保存在独立的 `queue.db` 中，手工删除录音文件不会同步清理数据库记录；所有非完成记录都被计入待上传，缺失文件会永久重试。
- 根因二：手动补传在 worker 命令处理线程内同步遍历整个队列，长队列会占住命令锁，使录音命令等待或超时。
- 根因三：麦克风启动失败后，worker 抛出命令拒绝前没有发布最终状态快照；渲染进程也没有等待和显示操作错误，因此用户只能看到按钮“无反应”。
- 修复：启动时及手动补传前核对本地文件；缺失文件保留为诊断记录，但不再计入待上传或重试。手动补传改为后台执行；开始录音失败时立即发布真实状态；开始、暂停、停止和补传操作增加进行中与错误反馈。
- 数据边界：不删除 `queue.db` 历史记录，不删除任何仍存在的录音文件，不修改服务端接口或上传协议。

## WIN-REC-007：未绑定时误阻止更新，系统默认麦克风无法启动

- 状态：已定位并修复，等待 `v0.2.0-codex.10` Windows 真机复测
- 影响版本：`v0.2.0-codex.9`
- 用户现象：尚未绑定时，已下载更新仍提示“录音中不能安装”；绑定后旧队列正常显示，但开始录音失败，最近错误为 `No input device matching "default"`；设置页无法选择真实麦克风，录音目录也缺少文件夹选择入口。
- 根因一：更新安装门禁使用派生后的综合录音状态。未绑定等安全阻塞状态会派生为 `recording_error`，被错误地当作非空闲采集状态。
- 根因二：首次配置会把界面值 `default` 转换为空设备选择器，但后续设置保存把字符串 `default` 原样写入 worker。PortAudio 将其当作真实设备名，因此无法打开系统默认麦克风。待上传队列与该录音失败没有因果关系。
- 修复：更新安装只在 worker 真实处于 `starting` 或 `recording` 时阻止；worker 加载和保存设置时把旧的 `default` 规范为系统默认设备；设置页通过受限 IPC 读取真实输入设备并提供下拉选择；首次部署提供目录选择器，部署完成后保留目录锁定并提供“打开文件夹”。
- 数据影响：不删除、不迁移现有录音文件和待上传队列；11 段历史待传仍由原队列继续补传。
- 防回归：新增更新门禁、旧麦克风配置迁移、设备列表控制协议、麦克风下拉框和目录选择器测试。

## WIN-REC-006：服务端绑定成功但客户端仍显示未绑定

- 状态：已定位并修复，等待新候选安装包真机复测
- 影响版本：`v0.2.0-codex.8`
- 用户现象：首次绑定已在服务端成功落库，但客户端提示“绑定失败”并继续显示未绑定；再次提交时服务端提示设备已绑定其他班级或教室。
- 根因：绑定接口返回公共响应 `SimpleSuccessVO`，其字符串内容为 `success`；客户端只接受布尔值 `true` 或 `success=true`，误把真实成功响应判为失败，因此没有继续向 worker 执行 `apply_binding`，服务端和本地绑定状态发生分叉。
- 修复：绑定和解绑操作同时兼容公共响应的根级或 `data` 内 `content=success`；非成功响应优先展示 `message` 或 `msg`，不再丢失服务端业务原因。业务异常码不能被误判为成功。
- 防回归：新增公共成功响应、非成功业务文案和业务异常码不得视为成功三项协议测试。

## WIN-REC-005：历史测试设备编号进入正式绑定请求

- 状态：已定位并修复，等待新候选安装包真机复测
- 影响版本：`v0.2.0-codex.7`
- 用户现象：Passport 登录、班级选择均成功，确认绑定时服务端收到 `WIN-REC-002-LOCAL-FIXTURE`，绑定无法完成；客户端左侧显示为 `WIN-·TURE`。
- 根因：测试电脑非系统盘的旧 worker 配置仍保留历史真机测试夹具。首次绑定时，控制器无条件优先采用持久化 `deviceNo`，没有验证它是否为规范物理网卡 MAC，因而覆盖了客户端本次解析出的真实 MAC。
- 修复：只有 12 位十六进制 MAC（允许旧配置带 `:` 或 `-` 分隔符）才可作为持久化设备编号继续使用；测试夹具、机器名和其他非法旧值一律忽略，改用当前物理网卡 MAC。绑定成功后，worker 通过既有 `apply_binding` 流程把真实 MAC 写回配置。
- 防回归：新增“非法测试夹具回退到物理 MAC”“分隔符 MAC 规范化”“解析结果不是 MAC 时拒绝绑定”自动化测试。

## WIN-REC-004：Passport 已进入首页但客户端未读取身份

- 状态：已定位并修复，等待新候选安装包真机复测
- 影响版本：`recorder-v0.2.0-codex.4`
- 用户现象：Passport 提示登录成功并进入数智家校首页，但客户端一直没有取得登录身份；进入班级教室后仍提示登录状态失效。
- 根因一：登录地址配置的成功回跳目标是 `https://szjx.xxt.cn/`，客户端却明确忽略该首页，只在进入 `szjx-console.xxt.cn` 时读取当前用户。
- 根因二：`.4` 错误地把 `webId` 和 `Authorization` 作为年级班级接口的必要条件。现役接口实际只需要同一 Passport 会话的 Cookie，以及 `{"schoolId":null}` 请求体。
- 修复：同时接受 `szjx.xxt.cn` 首页和 `szjx-console.xxt.cn` 作为身份读取触发点；年级班级接口直接请求配置中的 REST 地址，只复用隔离 Passport 会话的 Cookie，不读取或发送 `webId`，请求体固定为 `{"schoolId":null}`。
- 防回归：新增“登录回到首页即读取身份”“身份不要求 webId”“年级班级请求不含 Authorization 且 schoolId 为 null”的自动化测试。

## WIN-REC-003：切换接口环境被录音目录锁定错误阻断

- 状态：已定位并修复，等待新候选安装包真机复测
- 影响版本：`recorder-v0.2.0-codex.3`
- 用户现象：客户端默认显示测试环境；Passport 登录后查询目录提示登录状态失效。切换正式环境并保存时，又提示“录音数据目录首次部署后不可修改，需重新部署”。
- 根因一：设置页把已锁定、不可编辑的录音目录仍作为普通设置提交。Windows 路径表示与启动时记录不完全一致时，被错误识别为目录迁移，连带阻断接口环境保存。
- 根因二：新部署默认接口仍指向测试环境，不符合学校正式使用流程。
- 根因三（已被后续真机证据修正）：当时把年级班级接口失败误判为缺少 `webId` 授权；该判断不成立，完整修正见 `WIN-REC-004`。
- 修复：已锁定的录音目录不再进入普通设置更新；正式环境改为新部署默认值；测试环境仍可在设置中主动选择；现有录音目录、录音文件和待上传队列均不迁移、不删除。Passport 与年级班级接口的后续修复见 `WIN-REC-004`。
- 防回归：保留“锁定目录不进入普通设置更新”“首次部署仍提交所选目录”“新部署默认正式环境”自动化测试。

## WIN-REC-001：0.1.17 安装后主进程缺少模块

- 状态：已定位并修复；失败 Release 已删除
- 影响版本：`recorder-v0.1.17-beta.1`
- 用户错误：`ERR_MODULE_NOT_FOUND`，`src/main.js` 无法导入 `src/runtime-state.js`
- 根因：`electron-recorder/package.json` 的 `build.files` 是手工白名单，遗漏 `src/runtime-state.js`
- 修复提交：`450b0f5 fix(recorder): include runtime state in Windows package`
- 防回归：`src/package-resources.test.js` 从主入口递归检查所有相对 import 是否都包含在 `build.files`

### 复盘

原有测试只检查 worker 和 FFmpeg 是否存在，没有检查 Electron 主进程依赖闭包。此事故不是用户电脑造成的。

## WIN-REC-002：0.1.18-beta.2 真实安装后启动体验异常

- 状态：已在 Windows 10 x64 真机复现、修复并由新构建的本地 Setup 完成正常启动、worker 与真实麦克风验收；尚未发布新版本
- 首次报告：2026-07-14
- 影响版本：`recorder-v0.1.18-beta.2`
- 已知现象：干净首次启动正常打开，但在未配置数据盘时显示“请先选择非系统盘录音目录”；保存合法 E 盘目录后 worker 能启动，但会弹出可见控制台窗口。安装器本次还默认安装到系统盘 per-user Programs 目录。
- 当前结论：用户截图是预期的首次配置阻塞状态，不是 `WIN-REC-001` 的主进程缺模块错误。现场确认 `app.asar` 包含 `runtime-state.js`。可重复的 packaged 缺陷是 worker 构建未使用 Windows 无控制台子系统；`--noconsole` 修复后，本地候选 Setup 已明确安装到 E 盘并通过正常启动、无窗口 worker、真实录音和 Electron 重连验收。安装器仍允许用户选择系统盘，部署时必须继续把非系统盘选择作为门禁。
- 脱敏证据摘要：`docs/windows-recorder/evidence/WIN-REC-002-summary.md`

### 已确认的测试缺口

GitHub workflow 的 `Run packaged application smoke test` 设置 `ELECTRON_SMOKE_TEST=1`。`src/main.js` 在该模式下使用假的 WorkerClient 和假的 endpoint，只验证：

- Electron 主进程能够加载被打包的 JS 模块；
- renderer、preload、主窗口、悬浮球和设置弹窗能够渲染；
- 页面没有明显溢出。

它没有验证：

- 无测试环境变量时的正常启动；
- 首次启动、非系统盘配置和 locator 文件；
- `ClassroomRecorderWorker.exe` 能否真正启动；
- worker 的 PyInstaller 动态依赖和 PortAudio；
- loopback endpoint/token、detached 进程和重连；
- 麦克风录音、FFmpeg 编码和队列落盘。

### Windows 真机必须采集的原始证据

在修改代码前保存到一个新的本地诊断目录，不要提交令牌、密码、学校数据或真实录音：

1. 错误弹窗完整截图和可复制错误文本。
2. Windows 版本：`winver` 和 `Get-ComputerInfo | Select WindowsProductName, WindowsVersion, OsBuildNumber, OsArchitecture`。
3. 安装包文件名、来源 URL 和 SHA-256。
4. 实际安装目录和 `resources` 目录清单。
5. 是否为覆盖安装；旧版本是否卸载；同机是否运行过 Portable。
6. 正常启动控制台输出和退出码。
7. `%LOCALAPPDATA%` 下本应用 userData 中 locator 是否存在；只记录路径和结构，发布前脱敏内容。
8. 非系统盘 `.classroom-recorder`、`runtime`、配置和日志是否生成；内容必须脱敏。
9. worker 是否出现于任务管理器，手动运行 worker 时的标准错误。
